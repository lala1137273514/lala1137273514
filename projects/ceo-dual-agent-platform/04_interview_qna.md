## 一、项目定性类

### Q1: 这个项目到底是什么？你怎么定义它？

- **追问意图**: 验证你能否一句话讲清项目性质，以及你对商业模式的理解。
- **核心回答**: CEO 大模型是快商通基于 **Agent 架构**的 AI 销售效能平台。它不是一个聊天机器人或单点 AI 功能，而是一个连接了 5 大数据源（CRM/KICP/在线客服/企微/见鱼）的完整 AI 产品体系，覆盖 **管家 Agent + 销售 Agent** 双 Agent 架构下的 8+ 功能模块。项目当前面向公司内部运营（**To B 内部 CRM**），后续规划转型为 **SaaS 平台对外出售**，走「自用验证 → 外售」的双轮模式。
- 🔄 反问: 你们做的 AI 产品是面向内部还是外部客户？
- **L2 追问: "自用 → 外售"你怎么看这个策略？**
  - 🟢 安全: 先内部验证 PMF（产品市场匹配），再做 SaaS 化改造，风险可控。
  - 🟡 注意: 内部产品和外售产品在权限、多租户、定价等方面差异大，不能简单等同。
- **L3 追问: 你参与了 SaaS 转型的规划吗？**
  - 🔴 危险: 我不是 SaaS 转型的决策者。
  - 防线: 我参与的是打磨产品能力阶段，SaaS 转型属于公司战略层，我了解方向但不主导决策。

### Q2: 管家 Agent 和销售 Agent 的架构你是怎么设计的？

- **追问意图**: 测试你对 Agent 架构的理解深度——是否真正理解"Agent"含义。
- **核心回答**: 我按业务角色拆分为两个 Agent：**管家 Agent** 聚焦存量客户续费运营（90 天到期管理 + 客户画像 + AI 回访话术 + 客户时间线），**销售 Agent** 聚焦增量销售提效（AI 考试系统 + 经理日报 + 工资计算器 + 商机 KP 分析）。两个 Agent 共享底层数据（ETL 聚合的数仓），配套钉钉播报工具矩阵形成闭环。关键是 Agent 不只是"查询工具"，它能**主动推送**（如到期预警、风险客户提示）和**智能分析**（如日报自动诊断销售行为）。
- 🔄 反问: 你们对 Agent 的定义更偏"工具调用型"还是"自主决策型"？
- **L2 追问: 这两个 Agent 之间有协同吗？**
  - 🟢 安全: 通过共享客户数据实现协同——销售签单后客户进入管家续费池，管家的客户使用数据反馈给销售做 Upsell 判断。
  - 🟡 注意: 当前协同主要在数据层，Agent 之间还没有做 Multi-Agent 协作。坦诚说明现状。

## 二、AI 技术能力类

### Q3: 你为什么选择 Dify 来做工作流编排？

- **追问意图**: 看你的技术选型与取舍能力——是否理解工作流编排平台的价值。
- **核心回答**: 核心原因是 **AI 产品需要可编排、可校验、可重试的工作流**。以考试出题为例，直连大模型 API 出题格式错误率 15%-20%（选项缺失/格式变体多），后端解析无法覆盖所有变体。Dify 让我把出题逻辑拆成「**生成→格式正则校验→异常修正重试**」三步，质量问题在流程中就被拦截。类似地，日报分析用 Dify 编排了「关键对话筛选 → BANT-C 分析 → 部门聚合 → 报告生成 → 推送」多步工作流。
- 🔄 反问: 你们目前用什么平台做 AI 工作流编排？
- **L2 追问: Dify 的局限是什么？**
  - 🟢 安全: 平台依赖风险（如 Dify 版本升级可能不兼容）、私有化部署增加运维成本、复杂逻辑仍需要代码节点辅助（如前置 Python 清洗）。
  - 🟡 注意: 不要过度神化 Dify，承认它只是工具，关键是编排思想。

### Q4: 你做的 Prompt Engineering 具体是什么？能讲技术细节吗？

- **追问意图**: 验证你是否真的懂 Prompt Engineering，还是只会说"写 Prompt"。
- **核心回答**: 以经理日报为例，上线后有两类问题：① **幻觉**（Compliance Bias）——输入无效数据模型也产出"完美"报告；② **归属错配**（Context Bleeding）——长 JSON 处理时客户归属搞混。我设计了三层防御：
  1. **防幻觉熔断协议**：在 System Prompt 最开头注入"必须先验证输入有效性"的指令，无效数据必须输出报错 JSON，严禁编造
  2. **溯源锚定机制**：强制模型在输出前先建立"客户↔销售"映射表，每次引用客户时回查归属
  3. **思维链强制校验（CoT）**：在`分析思考过程`字段中要求执行"数据验毒→归属映射→来源交叉检查"三步
  
  同时推动研发在 LLM 节点前增加 **前置 Python 代码节点**，做结构扁平化 + 强制标签注入 + 空值拦截。
- 🔄 反问: 你们的 AI 产品有做过防幻觉机制设计吗？
- **L2 追问: 你怎么验证修复效果？**
  - 🟢 安全: 用问题复发率和人工复核反馈作为阶段性证据。
  - 🔴 危险: 没有完整的 A/B 实验。坦诚说这是阶段验证，不虚构实验结果。

### Q5: 你做的 RAG 应用具体是什么场景？

- **追问意图**: 验证你对 RAG 的理解——是否知道知识库构建与检索增强的实际应用。
- **核心回答**: 管家 AI 回访话术功能采用 RAG 架构。我们构建了产品知识库（快商通各产品线介绍、客户 FAQ、续费话术最佳实践），设计了 **6 大回访场景模板**（标准回访、续费提醒、客诉处理、新客 Onboarding、增购推荐、流失挽回）。工作流程是：RAG 检索相关知识 → 结合客户画像信息（行业/合同金额/使用数据）→ Prompt 动态组装 → 生成个性化话术。
- 🔄 反问: 你们的 RAG 知识库是怎么做更新维护的？
- **L2 追问: 知识库质量怎么保证？**
  - 🟢 安全: 设计了高转化话术打标签规则，一线使用反馈驱动知识库迭代。
  - 🟡 注意: 当前 RAG 效果主要靠场景模板和 Prompt 质量，知识库更新机制还需要持续优化。

## 三、数据治理类

### Q6: 为什么管家数据聚合选 ETL 而不是实时 API？

- **追问意图**: 测试你对性能/一致性/时效性的平衡能力。
- **核心回答**: 管家场景对实时性要求不高（T+1 可接受），但对**查询速度和跨系统关联分析**要求极高。ETL 方案的优势：① 在数仓层完成预计算和字段标准化；② 避免在线聚合抖动；③ 可以做跨系统关联分析（如将 KICP 渠道数据与 CRM 合同到期日关联判断续费风险）。实时 API 的问题是：5 个系统接口稳定性不一致，请求延迟从 50ms-3s 不等，实时聚合体验会很差。
- 🔄 反问: 你们业务里"准实时"和"一致性"通常怎么排序？
- **L2 追问: 如果业务突然要求实时怎么办？**
  - 🟢 安全: 做分层——核心看板保留 ETL，关键事件（如大额商机变更）可补增量同步通道。
  - 🟡 注意: 承认成本和复杂度都会上升。

### Q7: 你处理数据口径冲突的具体案例是什么？

- **追问意图**: 判断你是否理解"数据产品可信性"的核心问题。
- **核心回答**: 管家 Agent 上线后，发现**百度渠道的开口率异常偏高**。排查发现：百度用「对话 ID 去重」（1 访客 1 天多次对话算多次），其他渠道用「访客 ID 去重」（1 访客 1 天多次访问算 1 次）。同一个指标因为去重口径不同，数据不可直接比较。我的处理方式：
  1. 和数仓确认底层数据结构差异
  2. 在 PRD 中明确各渠道的去重规则
  3. 在数据展示页增加"数据口径说明"浮窗
  4. 形成规范：**数据产品必须"先定义口径再展示数据"**
- 🔄 反问: 你们的数据产品有口径审核机制吗？
- **L2 追问: 口径冲突会造成什么业务风险？**
  - 🟢 安全: 业务方把不可比较的数据当成可比较，导致错误资源分配；更严重的是打击系统可信度，一线不敢用。

## 四、方法论与边界类

### Q8: 你对 AI 产品质量保障的方法论是什么？

- **追问意图**: 看你是否有体系化的 AI 产品思维。
- **核心回答**: 我总结为 **三层质量保障链路**：
  1. **输入层**：数据有效性校验（前置代码节点拦截无效输入）
  2. **处理层**：工作流编排（生成→校验→修正，而非单次 API）+ Prompt 防幻觉设计（熔断+溯源）
  3. **输出层**：口径治理（估算/精确分层标注）+ 结果可追溯性
  
  核心理念是：**AI 产品要先保证数据可信和 AI 输出可控，再放大模型能力**。
- 🔄 反问: 你们目前 AI 产品的质量保障体系是什么？

### Q9: 你在团队里的真实角色边界是什么？

- **追问意图**: 防止"全栈式夸大"。
- **核心回答**: 我是产品侧 Owner。**我做的**：需求调研（4 轮一线用户调研）、PRD 撰写（33 份）、方案取舍（如 Dify vs 直连 API）、Prompt 方案设计、数据表字段定义参与、上线验收和效果复盘。**团队做的**：研发负责编码与联调、数仓负责 ETL 实现、算法负责模型和工作流效果。**我的不可替代性**在于：跨模块的产品治理视角——避免"每个模块都对，但系统整体不可信"。
- 🔄 反问: 你们对 AI PM 角色更偏"策略型"还是"落地型"？
- **L2 追问: 那你写代码吗？**
  - 🟢 安全: 不写生产代码。但 Prompt 方案中的防幻觉协议、Python 前置清洗逻辑的需求和伪代码是我输出的，研发按我的方案实现。
  - 边界管理: 不把研发实现据为己有，但 Prompt 设计和质量方案确实是我的输出。

### Q10: 这些数字靠谱吗？94%、3000→600 是怎么算的？

- **追问意图**: 专打估算口径。
- **核心回答**: 我把指标分为两类。**精确项**（95.8%/83.3%/99%+/0 耗时）来自业务方确认和调研数据，可按公式现场复算。**估算项**（94%/3000→600/年省 3-5 万）我会显式标注为估算：94% 是按操作步骤时长测算；3000→600 是按团队规模×单人成本估算；3-5 万是年化区间。面试中我先讲口径再讲结论，不把估算说成精确。
- 🔄 反问: 你们对面试中的"估算指标"可接受的表达边界是什么？
- **L2 追问: 没有精确数据就别讲？**
  - 防线: 立刻切换到精确项。估算项主动降级，不争辩。

### Q11: 这套方法论如何迁移到新项目？

- **追问意图**: 看你是否有可复用的方法论。
- **核心回答**: 我会迁移五个核心方法：
  1. **Agent 架构思维**：按业务角色拆分 Agent，共享数据底座，各自专注场景
  2. **工作流编排而非单次调用**：任何 AI 生成内容都设计"生成→校验→修正"链路
  3. **Prompt 防御性设计**：System Prompt 必须包含边界条件处理（熔断/溯源/思维链）
  4. **数据口径前置**：多源数据产品必须先定义口径再展示
  5. **估算与精确分层治理**：面试和汇报中区分 derived/estimated
- 🔄 反问: 你们当前最想找的 AI PM 是偏 0→1 建设还是 1→10 优化迭代？
