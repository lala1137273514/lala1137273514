### S - Situation

CEO 大模型是快商通内部的 **AI 销售效能平台**（CRM 型），面向公司销售团队和管家团队提供 AI 驱动的运营工具矩阵。项目定位为 **To B 内部提效**，后续规划转型为 **SaaS 平台对外出售**，是公司战略级 AI 工程，由 CEO 直接关注。

- **平台规模**：覆盖 **管家 Agent + 销售 Agent** 双 Agent 架构，以及考试系统、经理日报、工资计算器、自动播报等 **8+ 功能模块**
- **数据体量**：接入 **5 大数据源**（纷享销客 CRM、KICP 机器人平台、在线客服系统、企微/工作手机、见鱼销售管理系统），通过 ETL 层聚合为统一数据底座
- **技术架构**：后端 Flask + Vue3 前端 + Dify AI 工作流 + APScheduler 定时任务引擎 + MySQL 数据仓库
- **团队规模**：约 8 人（1 产品 + 3 后端 + 1 前端 + 1 算法 + 1 数仓 + 1 业务方）
- **项目状态**：已上线运营，覆盖全公司约 50+ 名销售和管家

我接手时项目已有初版框架，但面临三类挑战：① AI 输出质量不稳定（考试出题格式错误 15%-20%、日报出现幻觉）；② 多源数据口径不一致导致业务不信任系统；③ 缺乏标准化的产品迭代流程和文档体系。

#### 🔧 Dify 工作流编排

我在项目中深度使用 **Dify 工作流编排平台**，设计了 4 条核心 AI 工作流：

1. **AI 出题工作流**：课件上传 → 文本解析 → Prompt 生成题目 → 格式正则校验 → 异常修正重试。将出题从"单次 API 调用"重构为**生成→校验→修正**三步链路，格式错误率从 15%-20% 降至 3% 以内（估算值）

#### 📝 Prompt Engineering 与 AI 治理

经理日报上线后出现两类典型 AI 质量问题，我主导设计了 **三层防御机制**：

**问题诊断**：
- **幻觉问题**（Compliance Bias）：无效输入也能输出"完美"报告，模型调用预训练知识编造内容
- **归属错配**（Context Bleeding）：长 JSON 数组处理时，销售 A 的客户被归到销售 B 名下

**我设计的 Prompt 治理方案**：
1. **防幻觉熔断协议**：在 System Prompt 中注入"零容忍幻觉"指令，强制模型先检查输入数据有效性，无效数据直接输出报错 JSON，严禁编造
2. **溯源锚定机制**：要求模型在输出前先建立"客户→销售"映射表，每次引用客户时必须回查归属，杜绝张冠李戴
3. **思维链强制校验**：在 `分析思考过程` 字段中要求执行"数据验毒→归属映射→来源交叉检查"三步思维链

**工程层加固**（我推动研发实施）：
- 前置 Python 代码节点：结构扁平化 + 强制标签注入 + 空值拦截，在数据进入 LLM 前完成物理清洗

#### 🗄️ 多源数据治理与 ETL

我参与设计了 **8 张核心数据表**的字段定义和数据流转逻辑，推动 **15+ 个 APScheduler 定时任务** 的产品需求：

- **数据表设计参与**：员工信息表、通话记录表（含 AI 分析字段）、聊天记录表、商机数据表（含 KP 分析字段）、客户信息表、每日对话分析表（含 BANT-C 分析）、部门维度分析表、语音通话记录表
- **数据匹配规则设计**：商机与客户通过 phone/wxAlias/friendWxId 三重匹配；通话/聊天/语音记录与商机通过 customer_info JSON 字段关联
- **定时任务编排**：涵盖数据同步（每小时）、AI 分析（每 40 分钟）、经理日报生成（11:00/17:00）、商机 KP 分析（11:00/17:00）等多时段调度

**关键决策**：推动管家数据聚合从"实时拉取多系统 API"改为"定时 ETL 入数仓"。管家场景对实时性要求不高（T+1 可接受），但对查询速度和跨系统关联分析要求极高，ETL 方案在数仓层完成预计算，实现一站式秒级查询。

我负责的是快商通 CEO 大模型——一个基于 Agent 架构的 AI 销售效能平台。它不是单点 AI 功能，而是连接了 CRM、KICP、在线客服等 5 大数据源的完整 AI 产品。项目目前面向公司内部运营，后续规划转型为 SaaS 对外出售。

**架构（25s）**  
我把产品拆分为管家 Agent 和销售 Agent 双 Agent 架构。管家 Agent 聚焦存量客户续费运营——90 天到期管理、客户画像、AI 回访话术；销售 Agent 聚焦增量销售提效——AI 考试系统、经理日报、商机 KP 分析。配套钉钉播报工具矩阵做运营闭环。  
🪝 钩子1（Agent 架构）：如果你感兴趣，我可以展开管家 Agent 的数据聚合方案——我们为什么选 ETL 而不是实时 API。

**AI 能力（35s）**  
我做了两类关键 AI 产品设计。第一是工作流编排：用 Dify 平台设计了出题、日报分析、KP 分析、回访话术 4 条工作流，其中出题工作流采用"生成→校验→修正"三步链路，解决了 AI 输出格式不稳定的问题。第二是 Prompt 工程：经理日报上线后出现幻觉和归属错配，我设计了防幻觉熔断协议、溯源锚定机制，从 System Prompt 层面杜绝无效数据编造和客户张冠李戴。  
🪝 钩子2（Prompt 治理）：这个防幻觉方案比较有意思，我可以讲完整的技术思路——为什么简单换模型解决不了。

**数据治理（20s）**  
数据层面，我推动了 5 大数据源的 ETL 聚合，参与了 8 张数据表的字段设计。过程中发现了百度渠道和其他渠道的去重口径冲突——对话 ID 和访客 ID 统计方式不同导致数据不可比较。我把口径说明前置到了 PRD 和展示层，建立了"先定义口径再展示数据"的规范流程。

**结果（25s）**  
最终成果是：考试从 4 小时到 10 分钟、日报从 2 小时到 30 分钟、播报从 1-2 小时到全自动。我的方法论是：AI 产品要先保证数据可信和 AI 输出可控，再放大模型能力。
