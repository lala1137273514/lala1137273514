## 二、业务背景与痛点

### 2.1 行业背景

2024-2026 年，大模型在企业场景的落地已从"能不能用"进入"用得好不好"的阶段。Prompt Engineering 作为连接模型能力与业务场景的关键环节，其管理和评测需求急剧增长。然而，大多数企业在 AI 产品落地过程中面临三个核心基建缺失：

1. **提示词管理无标准**：Prompt 迭代频繁但缺乏版本控制和质量分析能力，团队成员各自维护、难以复用和追溯。
2. **模型效果评测无体系**：依赖人工抽样判断效果，覆盖率低、主观性强，无法支撑快速迭代。行业虽有 Langfuse、LangSmith 等平台，但价格高昂（$59-$499/月）、接入成本大。
3. **工作流运行不可观测**：基于 Dify 等平台编排的工作流，运行过程中各节点的输入输出和异常无法实时追踪，问题定位依赖人工排查。

### 2.2 公司业务背景

快商通核心产品依托 Dify 工作流平台驱动多个 AI 业务模块（CEO 大模型、百度健康医生 IP Agent 等），业务团队日均运行数百条 AI 工作流 Case。随着产品线扩展，对 Prompt 统一管理、模型效果系统化评测、Token 调用成本可视化的需求日益紧迫。千锤 Agent 平台正是在此背景下立项，定位为公司级 AI 基础设施中台。

### 2.3 核心痛点分析

- **痛点 1：Prompt 迭代缺乏全生命周期管理——"写不好、管不了、优化没方向"**
  - 表现：AI PM 日均迭代 10-30 条提示词，版本管理靠手动文件命名（`v1.txt`、`v2_final.txt`），无法追溯"哪个版本效果最好"
  - 影响：每条提示词因缺乏结构化引导平均多花 **5-10 分钟**反复调试。按日均 15 条算，日均浪费 **75-150 分钟（约全天 15%-30% 的有效工作时间）**在 Prompt 调试上
  - 当前解决方式：凭经验手写 + Notion/文本文件存储，无 AI 辅助、无版本对比、无质量分析

- **痛点 2：大模型输出质量无体系化评测——"不知道好不好，发现不了坏的"**
  - 表现：CEO 大模型经理日报功能日均运行 **80-100 条** Case（5 个部门、每天 2 次），但效果评估依赖人工抽查，覆盖率不足 **5%**。曾出现 AI"张冠李戴"（销售归属错误）和幻觉问题，上线数天后才被发现
  - 影响：Bad Case 未被及时发现会直接影响业务决策（如将 A 客户的跟进信息归属到 B 销售），严重情况下可导致**客户流失/销售跟进错误**
  - 当前解决方式：人工抽样 + 主观判断，无自动化评测、无评分维度标准、无 Bad Case 自动筛选

- **痛点 3：Dify 工作流运行过程不可观测——"出了问题不知道哪个节点出的"**
  - 表现：Dify 工作流包含多个节点（数据提取→AI 分析→格式输出），运行失败或结果异常时，无法快速定位是哪个节点、哪个输入导致的问题
  - 影响：单次问题定位平均需 **30-60 分钟**手动逐节点排查，AI PM 和算法同事每周花费 **3-5 小时**在工作流问题排查上
  - 当前解决方式：查看 Dify 原始日志，缺乏结构化的 Trace 追踪和可视化

## 三、技术架构与选型

### 3.1 整体技术架构

千锤 Agent 平台的愿景是将多个 AI 基础设施模块融合为统一平台。**目前各模块独立开发、尚未融合**，后续计划整合为一体。我个人负责的是模块 ①②，模块 ④ 仅交付方案：

① **提示词管理模块**（YPrompt）【我负责，0→1 设计与落地】：提供提示词全生命周期管理——引导式对话生成（GPrompt 四步法）、AI 质量分析与优化建议、语义化版本控制（major.minor.patch + 标签分类）、多 AI 提供商统一抽象层。前端 Vue 3 + TypeScript，后端 Sanic 异步框架

② **大模型评测模块**（AI Dialogue Eval）【我负责，0→1 设计与落地】：基于 LLM-as-a-Judge 的全链路评测平台——支持单轮/多轮/Agent 三种评测模式 + Dify 工作流实时监控。核心组件包括统一评测调度器（eval_dispatcher）、可配置评估器系统（evaluator_store）、LLM 自动生成评估器（evaluator_generator）、Trace 追踪存储（trace_store）。**内含工作流 Trace 可视化功能**：通过"伪装成 Langfuse"的方式（实现 Langfuse 兼容的 `/api/public/ingestion` 端点 + HTTP Basic Auth），Dify 无需修改即可对接；`langfuse_adapter.py` 解析 trace-create / generation-create / span-create 三种事件，将工作流节点的 input/output/耗时/Token 消耗存储到 `langfuse_events` 表，自动触发评测。前端 Streamlit + Plotly，后端 Flask API Server + SQLite

③ **工作流编排模块**（公司已有独立项目）【非我负责】：公司基于开源 Dify 平台进行二次开发，本地化部署到公司服务器，支撑 CEO 大模型、百度健康医生 IP Agent 等多条 AI 业务线的工作流编排与运行。该模块作为公司已有的独立项目存在，千锤平台規划将其融合进来，我的评测模块通过 Trace 协议与其打通

④ **Token 消耗统计模块**【我仅交付方案】：设计了大模型调用成本的实时统计与可视化方案，支持按部门/工作流/时间维度的成本分析。离职前完成方案设计并交付，未进入开发阶段

> ℹ️ **平台融合状态说明**：千锤 Agent 平台的愿景是将以上模块融合为统一平台，但截至我离职时，各模块仍处于独立开发状态。我个人完成了模块 ①② 的 0→1 设计与上线，模块 ④ 仅交付方案，模块 ③ 为公司已有的独立项目。

### 3.2 技术选型过程

**评测引擎方案选型：**

| 对比维度 | 自建评测系统 | Langfuse | LangSmith |
|----------|-------------|----------|-----------|
| 定制性 | ✅ 完全可控 | 中（基于配置） | 中 |
| 成本 | ✅ 零额外成本 | $59-$499/月 | $39-$399/月 |
| Dify 集成 | ✅ 可深度适配 | 需要适配器 | 不直接支持 |
| 开发成本 | 较高（需从零搭建） | 低（开箱即用） | 低 |

**选型理由：** 考虑到公司的 Dify 工作流深度定制需求、成本控制要求以及未来扩展性，最终选择**自建评测系统**。参考 Langfuse 的 Trace 协议设计（OpenTelemetry 风格），实现自研评测引擎与 Dify 工作流的深度打通。自建方案虽然初期开发成本较高，但长期来看零订阅费用且可完全按业务需求定制评测维度。

**数据库演进：**

| 阶段 | 数据库方案 | 适用场景 | 演进原因 |
|------|-----------|---------|---------|
| MVP 阶段 | SQLite | 快速验证 | 零配置启动，快速跑通核心流程 |
| V2 阶段 | Redis + PostgreSQL + ClickHouse | 生产环境 | 需要动态凭证连接、多工作流隔离、高效分析查询 |

### 3.3 核心技术方案

**方案 1：LLM-as-a-Judge 评测体系**
- 设计目标：用 AI 替代人工做多维度评测，覆盖率从不足 5% 提升到 100%
- 具体方案：设计 1-5 分评分体系（`rubric.json` 配置化），定义两套评分维度体系：

  **对话评分体系（6 维度）：**

  | 维度代码 | 中文名称 | 评估重点 |
  |----------|----------|----------|
  | `clarity` | 表达清晰度 | 语句通顺、逻辑连贯，单句≥60字触发【长难句警告】 |
  | `proactivity` | 主动引导 | 需求挖掘、对话推进，避免【被动应答】 |
  | `content` | 内容价值 | 信息量、利益点突出，FAB 法则运用 |
  | `authority` | 专业权威 | 术语准确、信任建立，避免不确定词汇 |
  | `accuracy` | 信息准确 | 事实正确、无幻觉，无虚假承诺 |
  | `empathy` | 语气共情 | 亲和力、换位思考，像朋友一样交流 |

  **Agent 评分体系（4 维度）：**

  | 维度代码 | 中文名称 | 评估重点 |
  |----------|----------|----------|
  | `task` | 任务完成 | 目标达成情况 |
  | `tool` | 工具使用 | 参数正确性、工具选择（Tool Calls 分析） |
  | `reasoning` | 推理逻辑 | Thought 过程合理性（Chain of Thought 分析） |
  | `efficiency` | 执行效率 | 步骤冗余度 |

  每个维度均配置了 **5 级评分标准**（从 1 分到 5 分的具体描述）+ **低分自查清单**（`low_score_checklist`），确保评测可解释、可复现

- 综合分算法：`综合分 = min(平均分, 最低分 + 1.5)`——单纯平均分会掩盖某维度的严重问题，最低分惩罚确保重大缺陷（如幻觉、安全问题）能拉低整体分数，低于 3 分自动标记为 Bad Case 预警
- 统一评测调度器（`eval_dispatcher`）：自动识别输入数据类型（`messages` → 对话评测 / `task` + `tool_calls` → Agent 评测），路由到 `run_eval.py`（对话引擎）或 `agent_eval.py`（Agent 引擎），统一返回 `EvalResultDTO`（含 trace_id、scores、avg_score、analysis、meta）
- 效果：Bad Case 检出率大幅提升，驱动 Prompt 优化后实现 **Completion Token ↓14.4%、成本 ↓3.4%**

**方案 2：从离线评测到在线 Trace 追踪（"伪装成 Langfuse" 方案）**
- 设计目标：从手动拉取 Dify 工作流数据做离线评测，升级为自动接收实时数据做在线评测
- 具体方案：**核心思路是不修改 Dify，而是让评测平台"伪装"成 Langfuse**。Dify 原生支持将 LLM 调用数据发送到 Langfuse，我们只需实现 Langfuse 兼容的 API 端点，Dify 就能无感对接。具体实现：
  1. 实现 `/api/public/ingestion` 端点接收 Dify 推送的事件数据
  2. 实现 `/api/public/projects` 端点响应 Dify 的连接验证请求
  3. 支持 HTTP Basic Auth 认证（Public Key + Secret Key）
  4. `langfuse_adapter.py` 解析三种事件类型（`trace-create`、`generation-create`、`span-create`），同时保存原始可观测性数据（Token 使用、延迟、模型信息）和转换后的评测数据
  5. 评测系统自动触发评分，结果持久化到 `traces` + `scores` + `langfuse_events` 三张表
- 决策理由：离线评测需要人工导出数据、手动触发评测，效率低且时效性差。"伪装成 Langfuse" 方案让 Dify 零修改即可对接，实现"自动接收→自动评测→自动预警"的闭环
- 落地过程中解决了 4 个具体技术卡点：
  1. **Dify 配置验证失败（404）**：Dify 验证连接时会调用 `/api/public/projects`（非文档标注），需额外实现此端点
  2. **云端部署服务冲突**：Zeabur 自动检测到 Streamlit 命令并优先启动前端，忽略 Flask API Server，需手动配置为两个独立服务
  3. **前后端数据不互通**：API Server 和 Streamlit 前端在独立容器中，各自有独立的 SQLite 文件；解决方案是 Streamlit 通过 HTTP 调用 API 获取数据
  4. **原始 Langfuse 数据丢失**：初版只保存评测结果，丢失了原始可观测性数据（Token、延迟、模型）；新增 `langfuse_events` 表保留完整原始事件
- 效果：评测时效从"T+1（次日人工导出）"压缩为"实时（秒级触发）"，覆盖 5 个部门、日均 80-100 条 Case 的全量评测

**方案 3：可配置评估器系统（v1.0.0 升级）**
- 设计目标：让评测维度从"写死在 `rubric.json` 中"变为"用户可自定义配置"
- 具体方案：
  1. **`EvaluatorStore`**（评估器存储管理）：提供 `create` / `get` / `list` / `update` / `delete` / `set_default` / `create_version` 完整 CRUD + 版本管理 API。评估器数据结构包含 `evaluator_id`、`name`、`version`、`eval_types`（适用评测类型）、`dimensions`（维度配置含权重和 5 级评分标准）、`is_default`、`is_system`、`created_by`（manual / llm_generated / imported）
  2. **`EvaluatorGenerator`**（LLM 评估器生成器）：支持两种输入方式——`generate_from_text`（用户输入自然语言描述）和 `generate_from_document`（从文档提取评估标准）。生成后渲染为 Markdown 预览供用户确认/编辑，再保存
  3. **数据迁移**：`migrate_default_evaluator.py` 将原有 `rubric.json` 自动迁移为系统默认评估器（`is_system=True`），确保向后兼容
  4. **评测链路改造**：`run_eval.py` 从接受固定 `rubrics` 参数改为接受动态 `evaluator` 对象，通过 `_format_dimensions_with_weights` 动态生成含权重的评测 Prompt
- 决策理由：初版评测维度是全局固定的 1 套（6 个 hardcode 维度），但不同业务线（经理日报 vs 考试系统 vs 工资计算器）的评测重点完全不同。可配置化让每个业务线可以定制自己的评测标准
- 效果：从 1 套固定评估器升级为用户可自定义 N 套，支持不同业务场景的差异化评测

## 七、踩坑与解决

### 案例 1：评测维度权重不均导致 Bad Case 被"平均分"掩盖

- **问题描述**：初版评测系统设置了 6 个评测维度（准确性、完整性等），0-5 分制，低于 3 分标记为 Bad Case。但上线后发现，许多明显有问题的 Case 并未被标记——例如某条经理日报的"销售归属"完全张冠李戴（0 分），但其他 5 个维度都是 4-5 分，简单平均后总分为 3.3-4.2 分，未触发 Bad Case 预警
- **原因分析**：6 个维度采用等权重平均，单个维度的严重低分会被其余高分维度"稀释"。核心问题是：对于某些维度（如归属正确性），即使只有 1 个维度不通过，整个 Case 就应该标记为 Bad Case，而不是被平均分掩盖
- **解决过程**：
  1. 首先分析了 50+ 条被漏标的 Bad Case，归纳出低分维度的分布规律
  2. 引入**差异化权重机制**——核心维度（如归属正确性、数据准确性）权重提高
  3. 增加**最低分惩罚机制**——任何维度低于 3 分时，该维度分数会被放大计入总分，确保单个严重低分不被掩盖
  4. 调优后重新评测历史数据，验证 Bad Case 检出率显著提升
- **经验教训**：多维度评测体系中，**"平均分"是危险的**——它会掩盖关键短板。正确的做法是区分"可容忍的低分维度"和"一票否决的维度"，对后者引入惩罚机制。这个经验可迁移到任何需要多维度评估的 AI 产品场景（如客户画像质量评测、对话策略评测）

### 案例 2：从离线评测升级到在线评测时的 Trace 协议对接问题

- **问题描述**：初版评测系统是离线模式——手动从 Dify 导出工作流运行数据，导入评测系统打分。升级为在线评测时，需要让评测系统实时接收 Dify 工作流的运行数据，但在与 Dify 的 Trace 协议对接过程中接连遇到问题：API 未部署导致连接失败、数据库未部署导致动态凭证无法生成、不同工作流的数据混在一起无法区分
- **原因分析**：MVP 阶段使用 SQLite 本地数据库 + 静态凭证，快速跑通了核心流程。但升级到在线评测后，需要动态凭证来区分不同工作流的数据来源，而动态凭证依赖后端 API 和持久化数据库——这些基础设施在 MVP 阶段并未搭建
- **解决过程**：
  1. 通过竞品分析参考了 Langfuse 的 OpenTelemetry 风格 Trace 协议设计
  2. 临时方案：将静态凭证嵌入前端，跳过动态凭证生成，先跑通数据通路
  3. 长期方案：将数据库从 SQLite 升级为 Redis（凭证缓存）+ PostgreSQL（Trace 持久化）+ ClickHouse（分析查询），部署完整的后端 API 支持动态凭证
  4. 引入工作流级别的凭证隔离，确保每个工作流的 Trace 数据独立存储和查询
- **经验教训**：MVP "快速验证"的技术决策（如 SQLite + 静态凭证）会在后续升级时成为瓶颈。**在设计 MVP 时，应预留关键扩展点的接口**——即使不实现，也要在架构上为未来的动态凭证、多数据源隔离等需求预留空间。这个经验可迁移到任何"MVP 快速上线→逐步升级"的产品演进场景

### 案例 3：评测维度从固定到可配置的演进

- **问题描述**：初版评测系统只有 1 套固定评测维度，通过字符串注入到 Prompt 中让 LLM 评分。但不同业务线的评测需求差异巨大——经理日报需要重点评"归属正确性"，考试系统需要重点评"格式规范性"，工资计算器需要重点评"数值准确性"。1 套固定维度无法满足多业务线需求
- **原因分析**：MVP 阶段为快速上线，将评测维度硬编码在代码中。随着对接的业务线增多，每次需要修改评测维度都需要改代码、重新部署，不仅效率低，且维度配置与代码逻辑耦合
- **解决过程**：
  1. 设计了 Evaluator CRUD 系统——评估器作为独立实体存储在数据库中
  2. 每个评估器可定义独立的评分维度、权重、评分标准和提示词模板
  3. 新增 LLM 自动生成评估器功能——用户用自然语言描述业务场景，AI 自动生成结构化评估器配置
  4. 支持评估器版本管理和默认评估器设置，从 rubric.json 自动迁移为系统默认
- **经验教训**：AI 产品的评测标准应该像"配置"一样灵活，而不是像"代码"一样固定。**评测维度的可配置化是评测平台从"单项目工具"升级为"平台级基础设施"的关键转折点**。这个设计思路可迁移到任何需要多场景适配的 AI 质量保障体系

**个人成长总结：**

从「只知道手动判断 AI 效果好不好」到「用体系化方法构建 AI 质量评测闭环」的转变。这个项目让我深刻理解到：AI PM 不只是"设计 Prompt"和"写 PRD"，更要**建立一套可持续的 AI 质量保障机制**——让好的结果可复现，让坏的结果可定位、可修复。这个认知直接影响了我在后续项目（CEO 大模型经理日报优化、百度健康医生 IP Agent 迭代）中的工作方式。
