### 项目名称：千锤 Agent 平台 | 快商通科技
时间：2025.11 - 2026.02

### S - Situation 背景
> 公司多条 AI 产品线（CEO 大模型、百度健康 Agent 等）基于 Dify（本地部署二次开发）编排工作流，日均运行 80-100 条 Case，但模型输出质量完全依赖人工抽查（覆盖率不足 5%），曾发生经理日报"销售归属张冠李戴"等严重 Bad Case 上线数天后才被发现。公司规划建设千锤 Agent 平台将多个 AI 基础设施模块融合为统一中台，但各模块尚处于独立开发阶段。

### T - Task 任务
> 作为 AI PM 实习生，独立负责千锤平台中**提示词管理**和**大模型评测**两个模块的 0→1 方案设计与落地（另有 Token 消耗统计模块仅交付方案，工作流编排为公司已有独立项目，非我负责）。

### A - Action 行动

| 产品维度 | 具体工作 | AI PM 专业表达 |
|----------|---------|----------------|
| 评测体系设计 | 设计 1-5 分评分体系，对话场景定义 6 维度（清晰度/主动引导/内容价值/专业权威/信息准确/语气共情）+ Agent 场景 4 维度（任务完成/工具使用/推理逻辑/执行效率），每个维度配置 5 级评分标准 + 低分自查清单。设计综合分算法 `min(平均分, 最低分+1.5)` 解决高分掩盖单维度严重低分问题 | 搭建 LLM-as-a-Judge 评测体系，定义双场景（6+4）评分维度 + 最低分惩罚算法 + Bad Case 自动预警 |

## 二、简历版（新版三段式）

**千锤 Agent 平台（AI 基础设施中台）** | 快商通科技 | AI 产品经理实习生
2025.11 - 2026.02

**项目背景：**
公司基于 Dify（本地部署二开）编排多条 AI 业务线工作流，日均 80-100 条 Case（覆盖 5 部门），但模型输出质量依赖人工抽查（覆盖率不足 5%），曾发生 AI"销售归属张冠李戴"等 Bad Case 上线数天才被发现。千锤平台规划将提示词管理、评测、工作流编排等模块融合为统一中台，我独立负责其中**提示词管理和大模型评测**两个模块的 0→1 设计与落地。

**项目职责：**
- **评测体系搭建**：0→1 设计 LLM-as-a-Judge 评测平台，定义对话 6 维度 + Agent 4 维度评分标准（含 5 级评分 + 低分自查清单），设计综合分算法 `min(平均分, 最低分+1.5)` + Bad Case 自动预警

## 三、面试讲述脚本：千锤 Agent 平台

> 预计时长：2-3 分钟

### 🎬 开场（20s）

"我在快商通做的一个核心项目是千锤 Agent 平台——公司规划把提示词管理、评测、工作流编排这些 AI 基建融合成统一中台，我独立负责其中提示词管理和评测两个模块。**这个项目最核心的挑战其实不是技术实现，而是'怎么证明 AI 的输出是好的'**🪝。因为当时公司基于 Dify 本地部署的工作流已经跑起来了，日均有 80-100 条 Case 在运行，但效果好不好，完全靠人工抽查，覆盖率不到 5%。"

### ⚡ 挑战（25s）

"印象最深的是经理日报功能出了一个 Bad Case——AI 把 A 销售的客户归属到了 B 销售名下，'张冠李戴'。这个问题上线了好几天才被发现。因为没有评测系统，没有人能系统地检查每天几十条 AI 输出的质量。所以 mentor 给我定的方向就是：**建一套能自动发现 Bad Case 的评测体系**。"

### 🔧 方案（50s）

"我设计了一套基于 LLM-as-a-Judge 的评测系统。定义了对话场景 6 个评分维度和 Agent 场景 4 个维度，每个维度有 5 级标准和低分自查清单。**不过综合分算法其实是第二版**🪝——第一版只用了简单平均分，结果发现一个维度即使只有 0 分，被其他高分一平均，总分还能到 3 分多——Bad Case 被'平均分'掩盖了。后来我设计了 `min(平均分, 最低分+1.5)` 的惩罚机制，才真正把 Bad Case 检出来。

第二个挑战是从离线评测升级到在线评测。**我的方案是让评测平台'伪装成 Langfuse'**🪝——因为 Dify 原生支持往 Langfuse 发数据，我们只需要实现 Langfuse 兼容的 API 端点，Dify 就能零修改直接对接。这个思路落地过程中踩了 4 个坑，比如 Dify 验证连接时会调一个文档里没写的接口，还有云端部署时两个服务冲突的问题，都是通过加日志逐步排查解决的。

第三个是做了可配置的评估器系统——不同业务线评测重点不一样，我设计了评估器的完整 CRUD，还支持用 AI 自动生成评估器——用户用自然语言描述需求，系统自动生成结构化评分标准。"

### 📊 成果（20s）

"上线后，评测覆盖率从不到 5% 提升到 100%——日均 80-100 条 Case 全量自动评测。**通过评测发现的 Bad Case 驱动 Prompt 优化后，有个数据跟我预期差挺多**🪝——Completion Token 降了 14.4%，但总 Token 几乎没变，是通过精简输出而不是精简输入来实现的。同时成本降了 3.4%，延迟也减了 2.5 秒。"

### 💡 收获（15s）

"这个项目让我最大的认知转变是：AI PM 不只是'把功能做出来'，**更要建立一套能持续保障 AI 质量的机制**。评测不是一次性的事，而是一个'发现→定位→优化→验证'的飞轮。这个思路我后来在百度健康医生 IP Agent 的 Bad Case 迭代中也复用了。"

## 四、追问预案

| 可能被追问 | 追问意图 | 准备要点 |
|-----------|---------|---------  |
| "评测覆盖率 100% 的数据怎么来的？" | 验证数据真实性 | 所有通过 Trace 协议进入评测系统的 Case 都会被自动评分，100% 指的是系统覆盖率。目前对接的是 CEO 大模型项目的 5 个部门，日均 40-50 条 Case × 每天 2 次 = 80-100 条。这是系统统计的精确值。 |
| "你做了什么 vs mentor 做了什么？项目里其他模块呢？" | 角色边界 | Mentor 负责千锤平台的整体规划和优先级。我负责**提示词管理**和**大模型评测**两个模块的 0→1 方案设计与落地（评测维度定义、权重调优、Trace 协议设计、评估器系统方案、PRD 全部独立完成）。工作流编排是公司已有的独立项目（基于 Dify 二次开发），不是我负责的。Token 消耗统计模块我只交付了方案，未进入开发。各模块目前独立开发，尚未融合为统一平台。代码不是我写的，但所有 PRD 和方案设计由我独立完成。 |
| "为什么自建评测而不是用 Langfuse？" | 方案选型 | 三个原因：1）Langfuse 订阅费 $59-$499/月，年费不低；2）我们的 Dify 是本地部署二开的，需要与 Trace 协议深度适配；3）评测维度需要完全按业务需求定制，外部工具灵活性不足。但我参考了 Langfuse 的协议设计理念，核心方案是"伪装成 Langfuse"——实现兼容 API 让 Dify 零修改对接，"不重新发明协议"。 |
| "最低分惩罚机制具体怎么设计的？" | 技术深度 | 综合分算法 = `min(平均分, 最低分 + 1.5)`。含义是：即使平均分很高，只要有一个维度严重低分，总分也会被拉低。例如 5 个维度都是 5 分但归属正确性 0 分，平均分是 4.17，但 `min(4.17, 0+1.5) = 1.5`，直接触发 Bad Case 预警（阈值 3 分）。低于 3 分的 Case 还会自动触发根因分析，输出故障原因和 Prompt 修改建议。 |
| "如果重新做，你会怎么改？" | 反思能力 | 两个改进：1）MVP 阶段就应该预留动态凭证的接口设计，而不是先用静态凭证再重构——"伪装成 Langfuse"的方案本身是对的，但落地时踩的 4 个坑有一半可以通过更好的前期设计避免；2）评估器系统应该更早做，而不是等到有多条业务线需求后才做——提前产品化能节省大量后续适配工作。 |
| "Token ↓14.4% 但总 Token 没变？怎么回事？" | 数据理解 | 这说明优化方向是"精简输出"而非"精简输入"——Prompt 的 Token 实际上略微增加了（+4.2%，因为加了归属权校验等新机制），但 Completion Token 显著减少了 14.4%（AI 输出更精炼、减少废话）。总效果是成本 ↓3.4%，因为 Completion Token 的单价更高。 |
| "提示词管理模块和 YPrompt 的关系？" | 项目边界 | 千锤平台中的提示词管理模块是在公司内部需求下设计的初版。我后来利用业余时间将其独立开源为 YPrompt——增加了多 AI 提供商统一抽象层、双数据库适配、uTools 桌面插件等个人特色功能。两者的核心设计理念一致（GPrompt 四步生成 + 语义化版本控制），但 YPrompt 是更完整的产品化实现。 |
| "'伪装成 Langfuse'具体怎么实现的？" | 技术方案深度 | Dify 原生支持将 LLM 调用数据发送到 Langfuse。核心思路是不修改 Dify，而是让评测平台实现 Langfuse 兼容的 API：① 实现 `/api/public/ingestion` 端点接收事件数据 ② 支持 HTTP Basic Auth 认证 ③ `langfuse_adapter.py` 解析 3 种事件类型（trace/generation/span）④ 同时保存原始可观测数据和评测数据到 3 张表（traces/scores/langfuse_events）。落地时遇到 4 个卡点：Dify 验证时调了文档没写的 `/api/public/projects`、云端 Streamlit 和 Flask 服务冲突、容器间 SQLite 文件隔离、原始 Langfuse 数据丢失。 |
